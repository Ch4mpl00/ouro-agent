# Data Sources — агент собирает получение данных из workflow и MCP-tools

**Status:** pending
**Priority:** P3
**Area:** agent / workflow / mcp datasets and tools
**Created:** 2026-10-14
**Updated:** 2026-10-16

## Context

Пользователь передаёт ссылку/сайт и цель сбора. Агент исследует ресурс,
находит способ получения данных, создаёт dataset, собирает и проверяет
многоступенчатый процесс, затем настраивает его регулярный запуск.

**Согласованное направление:** общая логика конструктора и исполнения
живёт в текущем workflow на агентской стороне. MCP предоставляет инструменты,
хранение данных и внешние события. Отдельный pipeline executor внутри MCP
не строим. Базовая зависимость: [durable workflows](durable-workflows.md).

Регулярный запуск исполняет сохранённую версию без повторного planner.
LLM/Jev может быть явным шагом обработки, но не обязателен для сбора.
Ожидания, ремонт конфигурации и запросы уточнений пользователю поддерживает
общий agent workflow runtime.

[Исследование вариантов](data-sources-design.md) сохранено как материал
дизайна. Старый scope с fixed readers, отдельным MCP runtime и обязательной
news projection queue заменён этим направлением. Точные API/DSL и этапы
миграции предстоит спроектировать; функция пока не реализована.

## Acceptance

### Сценарий и компоненты

- Агент исследует ссылку через инструменты, находит RSS/Atom, публичный JSON
  API или доступную статическую HTML-структуру и выбирает способ извлечения.
- Процесс допускает pagination, list → detail, ограниченный обход,
  преобразования полей и fallback извлечения статьи. Эти конструкции
  принадлежат agent workflow; MCP-операции выполняют отдельные действия.
- Достаточно операций HTTP, parse feed/JSON/HTML, extract article и dataset
  read/write. Конкретное размещение чистых преобразований выбрать при
  реализации; общий control flow не переносится в инструменты MCP.
- Агент создаёт и проверяет процесс на репрезентативных примерах, сохраняет
  версию и настраивает cron-сигнал с идентификатором процесса и параметрами.
  MCP хранит/доставляет событие, но не интерпретирует определение процесса.
- Preview показывает промежуточные данные, покрытие страниц/ветвей и
  предполагаемые записи; production datasets и расписание не изменяются.
- Подключённый ресурс виден через список/статус: активный процесс, dataset,
  расписание, последний запуск и ошибки. Поддерживаются pause/resume.
- При устойчивой поломке формата запускается ограниченный цикл диагностики
  агентом, новая версия проверяется перед активацией. Сетевой retry сам по
  себе не требует LLM. Неоднозначность цели можно разрешить user input.

### Данные и границы владения

- MCP предоставляет datasets со свободным JSONB, описанием и необязательной
  схемой. Agent runtime не читает MCP-БД напрямую.
- Режим append сохраняет первую запись с данным ключом; upsert обновляет
  изменившееся значение. Равенство JSON не зависит от порядка ключей объекта.
- Идентичность записи определена явно; исходная тройка
  `(datasetId, sourceId, externalId)` остаётся рабочим вариантом.
  Изменение правила ключа или dataset требует явной миграции.
- MCP хранит инварианты данных: уникальность, revision/условное обновление,
  атомарные batches и идемпотентные операции. Run/step state, ожидания и
  последовательность действий хранятся в агентской БД.
- Checkpoint runtime продвигается после надёжной записи данных через MCP.
  Сбой между MCP commit и agent checkpoint безопасно повторяет запись
  благодаря устойчивому operation key. Между БД нет общей транзакции.
- Дочерние задания сохраняются до продвижения списка: detail, не полученный
  вовремя, не теряется при исчезновении записи из следующего top-N среза.
- Исходные данные доступны независимо от производных представлений.
  News — первый потребитель; её специализированная запись/индексация
  остаётся MCP-инструментом. Общую очередь процессов в MCP ради неё не строим.

### Ограничения и качество

- Guarded HTTP применяется к исходным URL, redirects, next links и detail
  URLs. Размеры ответов, число запросов/страниц, fan-out и время ограничены.
  Обрезанный RSS/JSON даёт ошибку, а не частичный успешный parse.
- Snapshot/top-N не обещает полноту после простоя; incremental pagination
  имеет явную семантику cursor, продолжения и достижения лимита.
- Отсутствие записи в неполном snapshot не означает удаление.
- Сбой отдельной записи виден и повторяем, успешные соседние результаты
  сохраняются. Ноль новых записей не считается доказательством schema drift.
- Browser-only сайты, новая auth/session automation и произвольный
  исполняемый код не требуются для первого среза. Агент сообщает о
  неподдерживаемом способе получения; scope расширяется по реальным кейсам.
- Управляющие tools/skill отделены от news-read. Тонкий MCP-доступ к
  управлению agent-owned процессами при необходимости делегирует запрос
  агентскому service, не создаёт второй runtime.

### Совместимость с текущими новостями

- Habr/HN постепенно перенести на сохранённые workflow из общих операций.
  Telegram provider/watermarks оставить на текущем пути.
- Сохранить sourceId habr/hackernews, URL-based news keys и интервалы
  30/15 минут. Seed не восстанавливает отключённые/удалённые конфигурации.
- При переключении не допускаются одновременно старый provider и новый
  процесс одного источника. Старые news_items не теряются и не создаются
  повторно; перенос всей истории в datasets не обязателен.
- list_news/search_news поддерживают динамические source IDs, fetch_article
  учитывает новые источники при поиске по URL.
- Сохранить находки ревью: news upsert должен корректно обновлять URL/дату;
  embedding пересчитывается при изменении индексируемого текста; поздний
  inline/backfill результат не прикрепляется к новой revision текста.

### Проверка

- Сквозные кейсы RSS → dataset → news, JSON list → pagination → detail,
  HTML list → article работают через один agent workflow runtime.
- Повторный запуск и restart не дублируют записи; ошибки detail, потерянный
  ответ MCP, частичный batch и изменение схемы имеют проверенное recovery.
- Отдельный тест показывает ожидание уточнения пользователем и продолжение
  процесса без блокирования других задач.
- Старые поиск/дайджесты и Telegram продолжают работать.
- Целевые Rust-тесты с fake HTTP/model/clock и тестовыми БД; build/dev и
  дополнительные production-поллеры не запускать.

## Notes

Порядок: durable workflow state/ожидания → недостающие data tools и
преобразования → authoring/preview/регулярный запуск → миграция Habr/HN.
Первый полезный процесс можно проверять до полной миграции новостей.
Jev — необязательная операция; общий solver на Jev не prerequisite.
