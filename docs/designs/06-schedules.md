# 06. Step 5: scheduled tasks on engine triggers

Status: draft (elephant) · Overview: [01](01-engine-migration.md) step 5,
decisions 2 and 4 · Epic: #62 · Engine: ouro 0.3.0, no engine change ·
Decisions log: [LOG.md](LOG.md)

## Problem

Scheduled tasks still run on the agent's own clock (`crates/agent/src/schedule.rs`):
cron rows in `scheduled_tasks`, a 30 s tick that claims a slot with a
compare-and-swap on `last_run_at`, logs it in `scheduled_fires` (whose id,
above 10⁹, becomes the signal id) and hands a `PendingSignal` to
`Supervisor::start`. The engine already has durable triggers: `cron` with
`metadata.ouro.timezone`, the one-shot `metadata.ouro.at`, overlap and
catch-up policies, a slot-derived run id fired once across workers and
restarts, `$run.schedule` (`slot`, `previous`), and the breaker that stops a
definition's schedule after N consecutive faults and hands on a
`ouro.definition.tripped` notice (ouro `docs/dsl.md`, `schedule`;
`docs/api.md`, breaker). Two clocks for one job is one too many.

Still parked for this step: `schedule_task(workflow: …)` answers
"unavailable until the schedules step" (design 03, R2-M5), the rest of
`crates/agent/tests/pending/skill_index.rs` and
`crates/mcp/tests/pending/skill_index_workflow.rs`, and the trip notice of a
scheduled definition (design 04, "step 5 decides trip notices").

## Decisions

1. **One definition per task, generated by the host.** `schedule_task`
   writes the YAML of definition `task-<id>` (template below), saves and
   activates it with `Runtime::activate_as(name, v, "agent", note)`. The
   agent's model never writes it: `save_workflow` refuses the `task-` name
   prefix, and the gate keeps refusing `schedule` (every kind) and now also
   `fire_scheduled` in agent versions. One path makes scheduled work: a task
   whose fire goes through the signal launch, so it gets host data, skills
   and the guard like any signal.
2. **A fire is a signal, as now.** The task's run calls one host function,
   `fire_scheduled { task, slot, previous }`. It builds the same
   `PendingSignal` the tick built (source `scheduler` or the task's own,
   the content header `Scheduled task #<id> fired. / Cron / Slot / Now /
   Previous fire / Recurring` and the prompt verbatim, the supervisor's
   `envContext`, `payload: {workflow}` for a task naming a saved workflow)
   and runs it through `Supervisor::start`, so fires still run one at a time
   with every other signal. `slot` and `previous` come from `$run.schedule`.
3. **The prompt is never an expression.** The task's text (prompt, source,
   workflow, cron, recurring) is stored in `document.metadata.agent.task`,
   not in `with`, and `fire_scheduled` reads it from its run's admitted
   definition (run access, `cx.run`). A prompt that happens to look like
   `${ … }` arrives verbatim.
4. **Fire ids are deterministic per engine run.** A fire's signal id is
   allocated once per task run id (`schedule:task-7:…`) in an agent table
   (a new migration, below), from 10⁹ + 1 up as now, so `scheduler:<id>`
   never lands on an MCP signal's trace. `fire_scheduled` is at-least-once:
   a re-dispatched call (a crash between the signal's admission and the
   call's record) gets the same id, and `start_named_root` returns the run
   that exists (step 0). One slot, one signal run.
5. **`fire_scheduled` waits for the signal's tree.** It returns what
   `run_active` returns: the signal's output; a fault (the signal's error,
   as a definite failure) when the signal faulted; `{"ok":true,"resumes":true}`
   when the tree suspended (a confirmation), which completes the task's run
   while the signal sleeps. A supervisor that is stopping (`start` → `None`)
   answers `FunctionError::interrupted`: the run stays recoverable and the
   call is sent again after the restart. The wait holds one drive and one
   function slot per running fire; tasks are few (`runs.rs` capacity).
6. **Faults count toward the task's breaker (reversible, for the
   maintainer).** A signal that faulted faults the task's run; three in a
   row trip `task-<id>` (engine default `Config::breaker_threshold`), its
   schedule stops and the engine hands on the notice. The signal's own
   `catch` has already told the user about each failure (recovery report);
   the trip is the runtime informing the agent that a task keeps failing.
   Alternative kept open: `fire_scheduled` completes on a faulted signal and
   only infrastructure faults count.
7. **A trip notice becomes one signal.** The engine's `EventSink` receives
   `ouro.definition.tripped` (id `tripped:<epoch>`, at least once). For a
   `task-` definition the agent starts a `scheduler` signal whose content
   names the task, its prompt, the trip's faults and last error, and says
   its schedule stopped and how to restart it (`schedule_task` again, or
   cancel). Its signal id is allocated by the same table, keyed by
   `tripped:<name>:<epoch>`: a redelivered notice starts nothing new. Trips
   of other definitions (loops, routes, saved workflows) keep design 04's
   behaviour (fallback, handover) and start no signal. What the agent does
   with the notice is skill text (`skills.default/scheduler.md`, a short new
   section), never Rust.
8. **Overlap `queue` by default, `catchup: latest`.** The tick awaited each
   fire, and a slot that came due meanwhile fired once, late: `queue` (one
   buffered slot, later ones skipped with a record) is that behaviour.
   `schedule_task` takes an optional `overlap` (`skip`, `queue`, `allow`,
   `replace`), written to `metadata.ouro.overlap`; its description says that
   fires still run one at a time with other signals, so `allow` only lets
   them wait in line.
9. **Time zone.** A task is saved with the user's zone at that time
   (`metadata.ouro.timezone`, read through `get_timezone`; UTC when unset).
   A background watch (every 60 s, in the supervisor, cancellable) reads
   `get_timezone`; when it differs from the zone last applied (memory key
   `schedule.timezone`), every active recurring `task-` definition whose
   zone differs is saved again with the new zone and activated (note
   "time zone <old> → <new>"), then the key is written. An unchanged zone
   saves nothing. One-shots keep their instant. The new epoch must neither
   fire again a slot the old one ran nor skip the next one (test 10).
10. **One-shots.** `cron_expr: "now"` → `metadata.ouro.at` = now (a past
    instant fires at the next tick). A non-recurring cron → `at` = its next
    slot after now on the user's wall clock, computed by the agent
    (`schedule.rs` §2 keeps `next_slot` for this and for validation). Its
    DST rule changes to the engine's (`docs/dsl.md`, timezone table): a
    fixed-time job in a gap fires at the first instant after the gap
    (03:00), no longer shifted by the jump (04:30), so a one-shot and the
    same recurring task agree.
11. **Cancel is a version without a schedule.** `cancel_scheduled_task(id)`
    saves and activates a version of `task-<id>` with no `schedule`/`at` and
    `metadata.agent.task.cancelled: true` (`do`: one `set`), which removes
    its triggers (engine: "a version without a schedule removes them").
    History stays in the store. An unknown, already cancelled or other
    definition's id answers `ok: false`. Ids are never reused.
12. **Listing reads the engine.** `list_scheduled_tasks` pages the control
    API's `definitions`, keeps the `task-` names whose active version is not
    cancelled, and answers per task: `id`, `cron_expr`, `recurring`,
    `prompt`, `source`, `workflow`, `overlap`, `timezone`, `created_at`,
    `next_fire` (the engine's next due time; `null` for a consumed one-shot,
    which is left out), `last_fire` (`previous` of the trigger, when the
    engine shows it), and `tripped` (the trip's faults and error, when
    tripped). `upcoming_fires` (three previews) is dropped: only the engine's
    own next due time is shown, so the list can't disagree with the clock
    that fires.
13. **Boot seeds, nothing imported.** Overview decision 2: tasks are
    recreated by hand, so MCP's `list_scheduled_tasks` import goes. The
    first start (memory key `schedule.initialized`, as now) creates the
    system `dreaming` task (`0 4 * * *`, source `dreaming`, same prompt) as
    a `task-` definition; never again, so a cancelled dreaming stays
    cancelled. `list_scheduled_tasks` stays in `SUPERVISOR_ONLY_TOOLS`
    (MCP still serves it).
14. **Removed:** `ScheduleStore`, `AgentDb`'s and `MemorySchedule`'s
    implementations, `tick`, `run_ticks`, `FireSink`/`SupervisorSink`, the
    MCP import, `preview_next_fires`, and the two tables (new migration:
    drop `scheduled_tasks` and `scheduled_fires`, create the id table of
    decision 4 and a task-id sequence; applied migrations never change). The
    sandbox's `DrySchedule` follows the new tool shape (a try's
    `schedule_task` is a write, mocked as now).

## Non-goals

- Agent-authored schedules on arbitrary workflows (`schedule` in
  `save_workflow`): one path, the task, until a real need.
- Running fires concurrently with other signals: the supervisor's one-at-a-time
  rule is not this step's to change.
- An engine API to delete or deactivate a definition (cancel by a
  schedule-less version is enough), or to preview several slots.
- Migrating prod's current tasks: the maintainer recreates them (Rollout).

## Design

### The task definition (`schedule.rs` §2)

```yaml
document:
  dsl: 1.0.0
  namespace: agent
  name: task-7
  version: 1.0.0
  metadata:
    ouro:
      timezone: Europe/Kyiv      # the user's zone when saved (decision 9)
      overlap: queue             # decision 8; or the tool's `overlap`
      # at: '2026-11-02T09:00:00+02:00'   one-shots, instead of `schedule`
    agent:
      task:
        id: 7
        cron: 0 9 * * *          # as the user gave it, `now` included
        recurring: true
        prompt: "…"              # verbatim, never evaluated (decision 3)
        source: null             # → `scheduler`
        workflow: null           # a saved workflow the fire runs
        created: '2026-10-26T12:00:00Z'
schedule:
  cron: 0 9 * * *
do:
  - fire:
      call: fire_scheduled
      with:
        slot: ${ $run.schedule.slot.iso8601 }
        previous: ${ $run.schedule.previous.iso8601 }
```

The cron is checked before saving as now (5 fields, a date that exists);
`Runtime::save` (`check()`) is the final word, and its error is the tool's
`ok: false`. The task id comes from the task-id sequence (decision 14), never
from listing names, so two concurrent `schedule_task` calls never write
versions of one name.

### `fire_scheduled` (`functions.rs`, registered at-least-once)

1. Read the run's admitted definition (`cx.run`) → `metadata.agent.task`.
   A missing task block is a definite failure (it cannot be an agent
   version: the gate refuses the function there).
2. Allocate the fire id for `ctx.run_id` (insert-or-get).
3. Build the `PendingSignal` (decision 2): content header with `Now` from
   the engine's clock, `Slot` and `Previous fire` from the arguments
   (`never (this is the first run)` when null).
4. `Supervisor::start` (a handle passed in at composition, as the tick's
   sink had: `main.rs` wires it, no global) → decision 5's answers.

### Trip notices (`runs.rs` or `schedule.rs` §3, an `EventSink`)

The sink sees every `ouro.definition.tripped`. For `task-*` it allocates
the notice's signal id (decision 7), then hands the signal to the supervisor
without waiting (a spawned, cancellable task: a sink must not hold the
engine's notify loop for a whole agent run) and accepts the event once the
id row exists. Other names: accepted, nothing started.

### Tools (`schedule.rs` §4)

`schedule_task { cron_expr, recurring, prompt, workflow?, overlap? }`:
validation as now; `workflow` must name a saved workflow with an active
version, else `ok: false` with the reason; answers `{ok, task: {id,
cron_expr, recurring, prompt, source, workflow, overlap, created_at},
timezone, next_fire}` (`next_fire` from the engine after activation).
`list_scheduled_tasks` and `cancel_scheduled_task` as decisions 11–12. The
tool descriptions in `synthetic_tools.json` say what changed: one-shots
leave the list once fired, a task that keeps failing stops (decision 6), and
`overlap`.

## Contract and model

No engine change, so no Quint change. The agent-side rules are pinned by
tests: one slot → one signal run (ids), the notice → one signal, cancel
stops, the zone watch is idempotent. The engine's trigger rules (slot ids,
overlap, catch-up, DST) are the engine's tests; the agent's tests use them,
they don't re-prove them.

## Failure modes

- **Crash during a fire:** the call re-dispatches; same fire id; the signal
  run resumes or is joined (decision 4).
- **Supervisor stopping:** interrupted, not faulted; the slot is neither
  lost nor counted (decision 5).
- **A long fire:** a later slot waits in the queue, more are skipped with a
  record (decision 8).
- **A task that keeps failing:** stops after three, one notice signal
  (decisions 6–7). During a model outage the notice's own signal may fail
  too; the engine has handed it on and the trip stays visible in
  `list_scheduled_tasks` (`tripped`).
- **Zone watch can't read the zone:** nothing is re-saved; it retries next
  round.
- **Store upgrade re-creating the store** (overview, risks): task
  definitions are gone with it; Rollout says to export them first.

## Tests

Test-first, in `crates/agent/tests/schedules.rs` (new) unless named. A
manual clock where the engine allows one (`with_clock`), else short real
slots (`at` a second ahead).

1. `schedule_task` recurring → `task-<id>` active with the cron, the zone and
   overlap `queue`; at its slot one `scheduler` signal runs, fire id > 10⁹,
   content header lines and the prompt verbatim; `previous` null then the
   first slot.
2. A prompt containing `${ .x }` arrives verbatim.
3. One-shot cron and `now`: each fires once; the list leaves it out after; a
   restart fires nothing again.
4. A re-dispatched `fire_scheduled` (the handler called twice for one run id)
   → one fire id, one signal run.
5. A stopping supervisor → the call is interrupted; after a restart the slot
   fires once.
6. Overlap: a fire still running when two more slots come due → one queued
   run after it, the other skipped with the engine's record.
7. Three faulted fires trip `task-<id>`; its schedule stops; exactly one
   `scheduler` notice signal naming the task and the error; the same notice
   delivered again starts nothing. A tripped loop definition starts no
   signal.
8. Cancel → no more fires, absent from the list, `ok: false` for a second
   cancel, an unknown id and a non-task id; a new task gets a new id.
9. `workflow: X` → the fire runs X's active version through
   `run_saved_workflow` (restore `tests/pending/skill_index.rs` and
   `crates/mcp/tests/pending/skill_index_workflow.rs` here); a missing
   workflow answers `ok: false` at `schedule_task`.
10. Zone change after a fire at 09:00 → one new version per recurring task,
    the next fire at 09:00 new local time, no extra fire; one-shots
    untouched; an unchanged zone saves nothing (versions count equal).
11. Gate: `save_workflow` refuses a `task-` name, a `schedule`, an `at`, and a
    call of `fire_scheduled`.
12. Boot: the first start seeds dreaming once; a second start seeds nothing;
    cancelled dreaming stays cancelled.
13. Validation: 6 fields, `0 0 31 11 *`, an invalid `overlap` → `ok: false`,
    nothing saved.
14. DST: a one-shot `30 2 * * *` created the day before a spring-forward gap
    in `Europe/Kyiv` gets `at` 03:00 local (`schedule.rs` unit test).
15. Sandbox: `try_workflow` of a draft that calls `schedule_task` records it
    as a mocked write; no `task-` definition appears in the real store.

Hand mutants (once, scratch copy): a fresh fire id per call (test 4); the
prompt written into `with` (test 2); the notice not keyed by epoch (test 7);
the zone watch saving on every round (test 10); cancel deleting nothing
(test 8).

## Rollout

(`sqlite3 -json … "SELECT * FROM scheduled_tasks"`) into the maintainer's
private notes, not the repo; recreate them by hand afterwards (overview
decision 2). Dreaming is seeded. No deploy without the maintainer.
