# 06. Step 5: scheduled tasks on engine triggers

Status: revised after goldfish round 1 (resolutions marked R-n) ·
Overview: [01](01-engine-migration.md) step 5, decisions 2 and 4 (one line
revised here, decision 10) · Epic: #62 · Engine: ouro 0.3.0, no engine
change · Decisions log: [LOG.md](LOG.md)

## Problem

Scheduled tasks still run on the agent's own clock (`crates/agent/src/schedule.rs`):
cron rows in `scheduled_tasks`, a 30 s tick that claims a slot with a
compare-and-swap on `last_run_at`, logs it in `scheduled_fires` (whose id,
above 10⁹, becomes the signal id) and hands a `PendingSignal` to
`Supervisor::start`. The engine already has durable triggers: `cron` with
`metadata.ouro.timezone`, the one-shot `metadata.ouro.at`, catch-up, a
slot-derived run id fired once across workers and restarts, and
`$run.schedule.slot` (ouro `docs/dsl.md`, `schedule`). Two clocks for one job
is one too many.

Still parked for this step: `schedule_task(workflow: …)` answers
"unavailable until the schedules step" (design 03, R2-M5), the rest of
`crates/agent/tests/pending/skill_index.rs` and
`crates/mcp/tests/pending/skill_index_workflow.rs`, and design 04's "step 5
decides trip notices".

## Decisions

1. **One definition per task, generated by the host.** `schedule_task`
   writes the YAML of definition `task-<id>` (templates below), saves and
   activates it (`Runtime::activate_as(name, v, "agent", note)`). The model
   never writes one: `save_workflow`, `start_child`/`start_named_child`,
   `launch` and `schedule_task(workflow:)` refuse the `task-` prefix
   (R-H2), and the gate keeps refusing `schedule`/`at` and now also
   `fire_scheduled` in agent versions.
2. **The engine's trigger only records the fire; the supervisor runs it
   (R-H1, R-H3, R-M7).** The task's run calls one host function,
   `fire_scheduled { slot }`, which inserts one row into `scheduled_fires`
   (insert-or-get by the engine run id, through `AgentDb::write`, R-L9),
   wakes the supervisor's fire drain and returns `{fire: <id>}` at once. The
   run ends in milliseconds: no handler holds the supervisor's permit, an
   engine drive or a function slot while an agent works, and nothing in the
   engine refers to the `Supervisor` (no cycle; the drain's `Notify` is an
   `EngineDeps` value). The drain is the tick's old sink fed from the table:
   it takes the oldest fire not yet run, builds the `PendingSignal` exactly
   as the tick did (source `scheduler` or the task's own, the header
   `Scheduled task #<id> fired. / Cron / Slot / Now / Previous fire /
   Recurring` and the prompt verbatim, `envContext` from `config.env_context`,
   `payload: {workflow}` for a task naming a saved workflow) and runs it with
   `Supervisor::start`, so fires still run one at a time with every other
   signal.
3. **Exactly one signal run per slot.** The fire's id (the signal id) comes
   from `scheduled_fires`' own sequence, so it continues above every id
   prod already used (R-M3). A re-dispatched `fire_scheduled` gets the same
   row. The drain marks a fire `started` before `Supervisor::start` and
   `done` after; a fire found `started` at boot is started again, and
   `start_named_root` returns the existing `signal:<id>` run (step 0), so a
   crash joins the run instead of repeating it. `start` → `None` (stopping)
   leaves the fire as it was for the next start; `--once` never starts the
   drain, so fires recorded then wait for the next normal start (R-M7).
4. **The prompt is never an expression.** The task's text (prompt, cron,
   recurring, source, workflow, zone, created) lives in
   `document.metadata.agent.task`; `fire_scheduled` reads it from its run's
   admitted definition (`cx.run(&cx.run_id)` → `Admission::definition`) and
   stores the rendered content in the fire row. A prompt that looks like
   `${ … }` arrives verbatim.
5. **`fire_scheduled` runs only at a trigger's root (R-H2).** It answers
   `not_executed` unless its run has no parent, its definition is `task-*`
   and its id starts with `schedule:task-`. Its `HostFunction.context` is
   its own (`task`), so `workflow_functions` never offers it to authors. The
   sandbox mocks it like a write: a try never records a real fire.
6. **`Previous fire` comes from the agent's table (R-M2).** It is the slot of
   the task's latest earlier fire row, so it survives every re-activation
   (a zone change, a restart) and the dreaming watermark stays right.
   `Slot` is `$run.schedule.slot`. After downtime the engine's
   `catchup: latest` fires once, for the oldest missed slot (the tick fired
   every missed slot, one per tick): the header shows that slot (R-L5).
7. **No trip notice signal (R-M5; revises overview step 5).** Because a
   task's run only records a fire, a signal's failure never faults it; the
   signal's own `catch` already reports each failure to the user. A task
   run faults only when recording fails (agent.db), which the agent cannot
   fix by deciding anything. Task definitions keep the engine's default
   breaker, so a task that can't even record stops instead of faulting at
   every slot; `list_scheduled_tasks` shows `tripped`. Nothing listens for
   `ouro.definition.tripped`.
8. **No overlap knob (R-M4).** Runs end at once, so overlap never applies;
   the definitions carry no `overlap`.
9. **Time zone (R-M1).** A recurring task is saved with the user's zone then
   (`metadata.ouro.timezone`, also copied into `metadata.agent.task.timezone`;
   UTC when unset). The supervisor's zone watch (every 60 s, cancellable,
   not in `--once`) reads `get_timezone` and, for each live recurring task
   (active version not cancelled, not tripped) whose stored zone differs,
   saves and activates a copy with the new zone. No memory key: the
   comparison per task is idempotent by construction (an unchanged zone
   saves nothing). Every `task-` write (`schedule_task`, cancel, the watch)
   holds one async mutex in the schedule seam and re-reads
   `definitions(name)` under it, so a cancel and a re-save can't interleave
   into a resurrected task. One-shots keep their instant.
10. **Store upgrades (R-L6, revises the overview's risk line).** The engine's
    store is the only copy of the tasks; "schedules re-generated" in the
    overview's Failure modes is replaced by the export procedure in Rollout,
    for this deploy and any future store re-creation.
11. **One-shots.** `cron_expr: "now"` → `metadata.ouro.at` = the engine
    clock's now (a past instant fires at the next tick). A non-recurring
    cron → `at` = its next slot after now on the user's wall clock. The
    agent's `next_slot` becomes the engine's rule, plain
    `croner::find_next_occurrence` on `now.with_timezone(&tz)` with the same
    croner version as the engine (R-M8), so a one-shot and the same
    recurring task agree; the tick's "shift by the jump" rule goes.
12. **Cancel is a version without a schedule.** `cancel_scheduled_task(id)`
    saves and activates a version of `task-<id>` with no `schedule`, no `at`
    and no `metadata.ouro` (R-L2), with `metadata.agent.task.cancelled:
    true`; that removes its triggers. A fire already recorded still runs.
    An unknown id, a cancelled task or a consumed one-shot answers
    `ok: false`. Ids are never reused.
13. **Listing (R-L1).** `list_scheduled_tasks` pages the control API's
    `definitions`, keeps `task-*` names with a non-empty `schedules`, and
    reads each one's active YAML (`runtime.definitions(name)`) for the task
    block. Per task: `id`, `cron_expr`, `recurring`, `prompt`, `source`,
    `workflow`, `timezone`, `created_at`, `next_fire` (the summary's due
    time), `last_fire` (its latest fire row's slot) and `tripped` (faults
    and error, when tripped). A one-shot is left out once its `at` has no
    due time and its fire is `done`. `upcoming_fires` (three previews) is
    dropped: only the engine's next due time is shown.
14. **Seeding (R-H4).** The first start under the new key
    `schedule.engine_seeded` creates the system `dreaming` task (`0 4 * * *`,
    source `dreaming`, same prompt) as a `task-` definition, never again;
    the old `schedule.initialized` is ignored, so prod gets dreaming back.
    MCP's import goes (overview decision 2); `list_scheduled_tasks` stays in
    `SUPERVISOR_ONLY_TOOLS`.
15. **A cap (R-H3).** `schedule_task` refuses past 50 live tasks (recurring
    or a pending one-shot): the list and the zone watch stay small.
16. **Removed and migrated (R-L4, R-M3).**
    - Code: `ScheduleStore` and its two implementations, `tick`,
      `run_ticks`, `FireSink`/`SupervisorSink`, the MCP import,
      `preview_next_fires`. Replaced by a `Schedules` seam (the runtime
      handle, the fire table, the id sequence, the write mutex) in
      `EngineDeps.schedule`; test fixtures and `crates/evals/src/optimizer.rs`
      pass its in-memory or agent.db implementation. `DrySchedule` goes if
      the sandbox's write mocking already covers the tools (R-L4).
    - Tests: `tests/supervisor.rs` and `tests/workflow_kinds.rs` fire through
      the drain; `crates/mcp/tests/schedule_handover.rs` loses its import
      test and keeps its zone test.
    - Migration (new file, applied ones never change): create `task_ids`
      (AUTOINCREMENT) with its `sqlite_sequence` row set to the old
      `scheduled_tasks` sequence; add `run_id` (unique), `previous`,
      `content`, `source`, `workflow`, `state` to `scheduled_fires`, keeping
      its rows and sequence; drop `scheduled_tasks`. A test opens a database
      with old rows and checks both sequences continue.

## Non-goals

- Agent-authored schedules on arbitrary workflows (`schedule` in
  `save_workflow`): one path, the task, until a real need.
- Running fires concurrently with other signals.
- An engine API to delete or deactivate a definition, or to preview slots.
- Migrating prod's current tasks: the maintainer recreates them (Rollout).

## Design

### Task definitions (`schedule.rs` §2)

Recurring:

```yaml
document:
  dsl: 1.0.0
  namespace: agent
  name: task-7
  version: 1.0.0
  metadata:
    ouro: { timezone: Europe/Kyiv }
    agent:
      task: { id: 7, cron: 0 9 * * *, recurring: true, prompt: "…",
              source: null, workflow: null, timezone: Europe/Kyiv,
              created: '2026-10-26T12:00:00Z' }
schedule:
  cron: 0 9 * * *
do:
  - fire:
      call: fire_scheduled
      with:
        slot: ${ $run.schedule.slot.iso8601 }
```

One-shot: `metadata.ouro: { at: '<RFC 3339 with offset>' }`, no `schedule`,
no `timezone`. Cancelled: no `metadata.ouro`, no `schedule`, `do: [{ cancelled:
{ set: { cancelled: true } } }]`, `metadata.agent.task.cancelled: true`.

Checked before saving as now (5 fields, a date that exists); `Runtime::save`
is the final word, its error the tool's `ok: false`. Task ids come from
`task_ids`, never from listing names. The tools' `now` is `engine.clock`
(R-L3).

### `fire_scheduled` (`functions.rs`, at-least-once, context `task`)

1. Decision 5's check → `not_executed`.
2. `cx.run` → the task block; missing → definite failure.
3. Under `AgentDb::write`: insert-or-get the row for `ctx.run_id` with the
   task id, slot, `previous` (decision 6), the rendered content, source and
   workflow, state `pending`.
4. Notify the drain; return `{fire: id}`.

### The fire drain (`schedule.rs` §3, spawned by `main.rs` unless `--once`)

Loop until cancelled: wait for the notify or 30 s; for each fire not `done`,
oldest first: mark `started`, `Supervisor::start(signal)`; `None` → stop the
round (the fire stays `started`, started again next boot, joined there);
otherwise mark `done` (a faulted signal is `done` too: its catch reported
it). `Now` in the header is the drain's clock when it builds the signal.

### The zone watch (`schedule.rs` §3)

Every 60 s: `get_timezone` (unreadable → skip the round); under the mutex,
for each live recurring task with another zone, save and activate the copy
(note `time zone <old> → <new>`).

## Contract and model

No engine change, no Quint change. Agent-side rules are pinned by tests: one
slot → one fire row → one signal run; a cancel stops; the zone watch is
idempotent and never resurrects.

## Failure modes

- **Crash between a fire row and its signal:** the row is `pending` or
  `started`; the next start runs or joins it (decision 3).
- **A long signal:** later fires wait in the table, in order; the engine
  records each slot once.
- **Recording fails (agent.db):** the task run faults; after three in a row
  the task stops and the list shows `tripped`.
- **Zone unreadable:** nothing re-saved; retried next round.
- **Store re-creation:** tasks are gone with it; Rollout's export first.

## Tests

Test-first, in `crates/agent/tests/schedules.rs` (new) unless named, on the
manual clock (`tests/support` `fixture_clocked`, `Engine.clock`; R-L3).

1. `schedule_task` recurring → `task-<id>` active with the cron and zone; at
   its slot one `scheduler` signal runs, fire id above the old sequence,
   header lines and the prompt verbatim; `Previous fire` never, then the
   first slot.
2. A prompt containing `${ .x }` arrives verbatim.
3. One-shot cron and `now`: each fires once; the list leaves it out after; a
   restart fires nothing again.
4. `fire_scheduled` called twice for one run id → one row, one signal run.
5. A stopping supervisor leaves the fire `started`; the next start joins the
   same `signal:<id>` run, no second one.
6. A signal still running while two slots come due → both recorded, run in
   order after it, the permit held by one signal at a time.
7. A faulted signal: the fire is `done`, the task stays live, no trip.
8. Cancel → no more fires, absent from the list; `ok: false` for a second
   cancel, an unknown id, a consumed one-shot; a new task gets a new id.
9. `workflow: X` → the fire runs X's active version through
   `run_saved_workflow` (restore `tests/pending/skill_index.rs` and
   `crates/mcp/tests/pending/skill_index_workflow.rs`); a missing workflow
   or a `task-` name answers `ok: false`.
10. On 2026-11-10 (winter: Kyiv UTC+2, Berlin UTC+1), zone `Europe/Kyiv` →
    `Europe/Berlin` at 10:30 Kyiv (09:30 Berlin) after the 09:00 Kyiv fire of
    `0 9 * * *`: one new version; next due 09:00 Berlin on 2026-11-11; `Previous fire` on that fire is the
    09:00 Kyiv slot; one-shots untouched; a second round saves nothing; a
    tripped task is not re-activated; a cancel racing the watch stays
    cancelled.
11. Refusals: `save_workflow` of a `task-` name, a `schedule`, an `at`, a
    call of `fire_scheduled`; a workflow that `start_child`s `task-N` gets a
    refusal and the supervisor stays live; `fire_scheduled` in a non-root
    run is `not_executed`.
12. Boot: a fresh database seeds dreaming once; a database with
    `schedule.initialized` already set (prod) seeds it once too; a second
    start seeds nothing; a cancelled dreaming stays cancelled.
13. Validation: 6 fields, `0 0 31 11 *`, the 51st live task → `ok: false`,
    nothing saved.
14. DST (`schedule.rs` unit): `30 2 * * *` in `Europe/Berlin` created the
    day before spring-forward → `at` 03:00 local, the engine's rule.
15. Sandbox: a try of a draft that calls `schedule_task` records it as a
    mocked write; no `task-` definition and no fire row appear.
16. Migration: old rows in `scheduled_tasks`/`scheduled_fires` → the next
    task id and fire id continue their sequences.

Hand mutants (once, scratch copy): a fresh row per `fire_scheduled` call
(test 4); the prompt written into `with` (test 2); `Previous fire` from
`$run.schedule.previous` (test 10); the zone watch saving every round (test
10); the root check removed (test 11).

## Rollout

Before deploying the engine migration: export prod's tasks
(`sqlite3 -json … "SELECT * FROM scheduled_tasks"`) into the maintainer's
private notes, not the repo, and recreate them by hand after the deploy
(overview decision 2); dreaming is seeded. The same export is the procedure
before any future engine store re-creation. No deploy without the
maintainer.

## Open questions

None blocking. Reversible: the cap of 50 (decision 15).
